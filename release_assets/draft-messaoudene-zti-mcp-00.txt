Abstract

   This document specifies an experimental security profile for the
   Model Context Protocol (MCP).  It binds delegated agent actions to an
   immutable mandate, preserves restrictions through delegation, and
   accounts for consumed and outstanding effects in a shared
   authorization registry.  The profile defines signed mandate and
   execution tokens, a deterministic cumulative policy gate, and current
   authorization at the provider's protected effect boundary.  An
   admission token is insufficient on its own: a conforming provider
   couples revalidation, unique consumption and its declared effect or
   irrevocable acceptance.  The profile addresses cumulative budget
   violations and explicitly represented forbidden combinations within
   an administered root scope.  It does not infer hidden human
   intentions, establish complete observation of activities outside that
   scope, or provide a generic transaction across arbitrary external
   services.

1.  Introduction

   An agent may delegate individually permitted subtasks to other agents
   or tools while the combined activity violates a shared restriction.
   An intermediary may also exercise its own credentials without
   retaining the restrictions of the originating mandate.  The protected
   object in this document is the authority exercised by the resulting
   actions, rather than the identity or reputation of the language model
   that proposed them.

   This document uses the term compositional constraint evasion for a
   sequence or concurrent set of actions that satisfies isolated checks
   but violates a stated cumulative policy.  The term is a local
   description, not a claim that every such case has one established
   threat taxonomy.  A confused-deputy problem is related but distinct:
   an intermediary can misuse authority even without a cumulative
   violation.

   ZTI-MCP is an application security profile carried over MCP.  It does
   not introduce a universal network router, change MCP transports, or
   give a gateway control over unmediated resources.  The same logical
   profile can use a gateway, sidecar or integrated execution
   controller.  Physical placement does not remove the provider
   integration obligations in Section 3.





Messaoudene                Expires 4 May 2027                   [Page 3]

   This revision selects one authorization contract: current-online.
   Admission creates a revocable reservation.  Authority is revalidated
   at the protected effect boundary, not merely when a request enters
   the network.  Rights acquired permanently at initial admission,
   offline acceptance, audit-only enforcement and fail-open behavior are
   not conforming fallback modes.

   The word Intent in the profile name refers to declared purpose as
   contextual input.  A signed statement establishes integrity and
   attribution under a trust configuration; it does not establish the
   truth of a human narrative.  The mandatory gate uses defined costs,
   restrictions and authoritative facts.  A semantic classifier, when
   used by a deployment, is a separately assessed source of evidence.

1.1.  Requirements language and document status

   Uppercase requirement terms have the meanings defined by BCP 14
   [RFC2119] and [RFC8174].  Lowercase uses are ordinary prose.  Every
   normative requirement in this document is a proposed requirement of
   this individual profile, not an amendment to the MCP specification or
   an adopted IETF standard.

   The baseline protocol version is MCP 2026-07-28.  Other revisions
   need an explicit binding and a new compatibility review.  The
   identifier zti-mcp/0.1 identifies this profile revision by private
   agreement.  This document is suitable for technical review as a
   complete individual draft candidate; an official submission and the
   normal editorial and community review processes remain separate
   actions.

1.2.  Scope and non-goals

   A root defines the administered scope of cumulative accounting.
   Global_Mandate does not mean that the registry observes all
   activities of a person, all roots, or all organizations.  The issuing
   authority determines which authenticated activities share a root.  A
   caller-selected correlation identifier MUST NOT create a new budget
   or bypass an existing authority scope.

   The base profile covers an immutable root policy, finite non-negative
   quantities, positive fact labels and monotone forbidden combinations.
   It does not define policy learning, general natural-language
   entailment, legal classification, refunds of gross consumed costs,
   periodic budget renewal, cross-root consensus, or a universal
   physical outcome detector.  These exclusions are necessary to state a
   testable contract.

2.1.  Roles and authenticated identities

   The Principal owns the delegated authority.  The Proposer is an agent
   or client that submits an action.  The Mandate Authority issues
   signed records under an established authorization policy.  The
   Gateway controls delivery to a protected downstream tool.  The
   Provider controls the protected effect.  The Recorder retains the
   authoritative transitions and results.  Components MAY combine these
   roles.

   [R01] The deployment MUST identify its trusted authority, registry,
   provider integration and authenticators.  Statements from a proposer,
   clientInfo, tool descriptions or an extension advertisement MUST NOT
   be used as proof of those trust assumptions.  The invoker identity
   used for authorization MUST come from the applicable authenticated
   channel or trusted local execution context.

   A proxy invokes a downstream resource with the identity and
   credentials that resource accepts.  The ICT sub claim names that
   authorized invoker.  It does not automatically name the human
   principal, which remains identified in the mandate.  If the proxy
   identity differs from the upstream delegatee, the authority MUST
   issue an attenuated child mandate naming the proxy before it issues
   the downstream ICT.  Rewriting sub alone is forbidden.  A proxy MUST
   NOT pass an unrelated upstream OAuth token to a downstream resource
   as a substitute for appropriate downstream authentication [MCP-AUTH].

2.2.  Root policy and inherited restrictions

   [R02] Each mandate MUST have exactly one parent, except the root.
   The registry MUST reject cycles, unknown parents, mismatched parent
   digests and chains longer than eight mandates, including the root.
   The issuer, tenant, principal, root and authority-assigned
   correlation identity MUST remain consistent throughout the chain.

   The root_policy object contains budgets and forbidden_sets.  It is
   present only on the root; child records contain root_policy: null and
   the same policy_hash.  The base profile has one cumulative budget
   vector per root.  It defines no independently replenished child
   budget and no child-specific cumulative fact policy.

   [R03] A child MUST only narrow allowed_executors, allowed_resources,
   allowed_methods and allowed_tools by set inclusion, reduce or retain
   every per-action cap, and use a validity interval contained in its
   parent interval.  It MUST NOT replace the root policy, omit a
   required restriction, change units, add a budget dimension, or treat
   an unknown constraint as permissive.  An empty allow-set authorizes
   no matching action.

   Checking JSON shape alone is insufficient to establish attenuation.
   The authority MUST apply these typed comparison rules.  It MUST
   resolve the complete authoritative lineage when reserving and
   consuming authority.  Copying a subset of restrictions into a token
   does not remove ancestor obligations.

   A delegation request MUST be authenticated as the parent delegatee or
   an explicitly authorized administrator.  A new child has a new
   immutable mandate_id and parent_hash.  Delegation, renaming, a new
   correlation label or another token signature MUST NOT reset root
   counters.  Changes to the root policy or replenishment require a
   separately defined migration protocol and are outside revision 0.1.

2.3.  Quantities, identifiers and canonical interpretation

   [R04] Budgets, action caps and cost bounds use a map from dimension
   name to {unit, amount}. Each map MUST contain exactly the dimensions
   of the root policy, including dimensions with zero cost.  Units MUST
   match exactly; conversion is outside the base profile. amount,
   authority_epoch and persistent revisions use canonical unsigned
   decimal strings in the range 0 through 18446744073709551615.  Leading
   zeros, signs, fractions, exponents and overflow MUST be rejected.







Messaoudene                Expires 4 May 2027                   [Page 7]

Internet-Draft                   ZTI-MCP                    October 2026


   The registry MUST use exact arithmetic or conservative integer checks
   that cannot create authority by rounding or overflow.  Boolean values
   MUST NOT be accepted as integer values.  JWT NumericDate claims and
   validity fields are JSON integers between 0 and 9007199254740991,
   with the stricter temporal relationships in Section 4.

   Identifiers are case-sensitive opaque strings unless a referenced
   standard defines them otherwise.  Set members MUST be unique.
   Providers MUST NOT introduce undocumented URI normalization, alias
   resolution, numeric coercion or wildcard matching.  Quantitative
   dimension names are ASCII strings of 1 to 64 characters using
   letters, digits, underscore, dot or hyphen.

   Within one configured authority domain, Operation_Key is (tenant_id,
   root_mandate_id, operation_id) and Reservation_Key is (tenant_id,
   root_mandate_id, reservation_id).  The issuer is resolved through
   that configured authority relationship.  Every mutation and lookup
   MUST validate the complete key and the authenticated caller rights.
   Identical short IDs in another tenant or root convey no authority.

   The Action_Binding and document digests use JCS [RFC8785] and UTF-8
   with SHA-256.  Duplicate object names, non-finite numbers, invalid
   Unicode and inputs outside the canonicalizer contract MUST be
   rejected before binding.  JCS property ordering and number
   serialization MUST NOT be replaced by a superficially similar
   general-purpose JSON pretty-printer.

3.  ZTI-MCP Architecture and Lifecycle

   A deployment first establishes the protected resource scope and
   trusted effect adapters.  It then issues a root mandate, registers
   attenuated descendants, reserves a proposed final action, forwards a
   valid ICT only on an authorized path, and consumes that reservation
   at the provider boundary.  The registry remains authoritative across
   transport connections and agent changes.

3.1.  Mandate creation and registration

   [R05] Root issuance MUST be authorized by an authenticated principal
   or issuing policy.  The issuing authority MUST select the accounting
   root; it MUST NOT accept a proposer-generated task label as proof of
   a fresh entitlement.  Root creation MUST identify the exact
   resources, operations, dimensions, units, policy and validity
   covered.

   The immutable zti_mandate object contains profile, tenant_id,
   principal_id, root_mandate_id, mandate_id, parent_id, parent_hash,
   correlation_id, delegatee_id, valid_from, valid_until, constraints,



Messaoudene                Expires 4 May 2027                   [Page 8]

Internet-Draft                   ZTI-MCP                    October 2026


   root_policy and policy_hash.  The root has null parent fields.  The
   constraints object contains exactly allowed_executors,
   allowed_resources, allowed_methods, allowed_tools and action_caps.
   Each child references its parent object digest.

   The mandate_hash is SHA-256(JCS(zti_mandate)).  The policy_hash is
   SHA-256(JCS(the root root_policy object)).  These values are
   lowercase hexadecimal strings of 64 characters.  They are commitments
   to document content, not to arbitrary JWS signature bytes.

   The signed mandate uses the distinct JWS type zti-mandate+jwt, ES256,
   and claims iss, sub, aud, iat, nbf, exp, jti and zti_mandate. sub
   equals delegatee_id; aud identifies the configured registry; nbf and
   exp equal valid_from and valid_until.  The registry MUST validate the
   signed record and its lineage before registration.  It MUST NOT
   accept an ICT or OAuth access token as a mandate.

   Mandate verification MUST use the same configured-key and ES256
   signing-input rules as the ICT, with exactly alg, kid and the
   mandate-specific typ in the protected header.  It MUST enforce the
   distinct complete mandate claim schema, reject duplicate or
   additional members, validate issuer and registry audience, require
   profile zti-mcp/0.1, safe-integer dates, iat <= nbf < exp, and
   valid_from < valid_until.  The ICT maximum lifetime of 60 seconds
   does not apply to a mandate; the issuing policy controls mandate
   lifetime.

   Registration of an already known mandate identity with identical
   immutable content MUST be idempotent and MUST preserve its current
   inactive status, counters and history.  Different content under that
   identity MUST be refused as a conflict.  A still-valid old signature
   MUST NOT reactivate a revoked mandate or reset its root.

   A registry MAY distribute immutable signed mandate records by
   reference rather than exposing every ancestor to every tool.
   References MUST resolve only through authenticated configured
   authority services.  Failure to resolve a required ancestor causes
   suspension or refusal; it does not permit execution with an
   incomplete chain.

3.2.  Action preparation, admission and non-delivery

   [R06] The trusted adapter MUST derive a conservative effect footprint
   from the final effective action, including cost bounds and possible
   fact labels.  A proposer's claimed costs or labels are untrusted
   hints.  Unknown footprint, unknown units, unsupported operations or
   an inability to establish a reliable bound MUST cause refusal or
   suspension before the protected effect.



Messaoudene                Expires 4 May 2027                   [Page 9]

Internet-Draft                   ZTI-MCP                    October 2026


   Defaults, transformations and routing that alter the protected
   operation MUST be resolved before the final binding, or cause a new
   authorization.  Mutable resources MUST be bound to an immutable
   version or a provider precondition checked at the protected boundary.
   The implementation MUST identify which mutable inputs its
   precondition covers.  An unchanged pathname is not evidence that the
   referenced contents are unchanged.

   [R07] Reservation admission MUST atomically validate the current
   lineage, derive or validate the footprint, evaluate the root gate
   over consumed and outstanding state, and store the unique
   reservation.  Signing and returning an ICT MUST occur only for a
   reservation that exists in authoritative state.  A lost token
   response does not justify creating a second reservation for the same
   operation.

   [R08] A gateway claiming non-delivery MUST complete its admission
   checks before handing the protected action to the downstream
   application.  A rejected action MUST NOT be forwarded through a
   diagnostic, retry, alternate route or audit path that delivers it to
   that application.  Necessary delivery of minimal decision data to
   trusted authorization components is part of the declared trust
   boundary, not prohibited downstream execution.

   An ICT identifies reserved authority.  It does not promise successful
   completion, establish the truth of declared purpose, or authorize
   execution after the mandate has become invalid.

3.3.  Provider synchronization barrier

   [R09] The provider MUST implement an AtomicEffect boundary that
   orders current revalidation, unique reservation consumption,
   accounting and the protected resource transition as one authorization
   unit.  This can be a shared transaction or a provider-coordinated
   commit mechanism with the same stated guarantees.  A remote check
   followed by an independent execute call does not satisfy this
   requirement.

   The protected transition MAY be a local resource mutation.  For a
   remote or physical provider, it MAY instead be the provider's
   durable, irrevocable acceptance of the exact operation, but only when
   the deployment explicitly defines acceptance as the protected
   boundary.  Such acceptance MUST make the operation uniquely
   accountable, prohibit later unvalidated substitution, and provide
   stable lookup.  It MUST NOT be a cancellable queue entry, an
   admission ticket, or a local promise to send the operation later.





Messaoudene                Expires 4 May 2027                  [Page 10]

Internet-Draft                   ZTI-MCP                    October 2026


   When acceptance is the protected boundary, subsequent completion is a
   different event.  A revocation ordered after acceptance does not
   retroactively undo that commitment.  This profile does not promise
   cessation of all physical activity at the instant a revocation
   request reaches a network interface.  A deployment requiring a later
   boundary MUST provide an enforcement mechanism at that later
   boundary.

   [R10] At AtomicEffect, the provider MUST use the authenticated
   invoker and final action, validate the ICT and current authoritative
   state, verify the full lineage, and confirm that the reservation
   remains usable.  It MUST bind the resulting transition to the
   operation_id and reservation_id.  If the provider cannot participate
   in this coupling, it MUST NOT claim strict ZTI-MCP conformance for
   that operation.

   The abstract AtomicEffect primitive is an integration requirement,
   not a generic distributed transaction algorithm supplied by a JWT.
   An implementation report MUST name the actual transaction or commit
   mechanism, its failure model and the provider acknowledgements it
   relies on.

   [R11] Only a RESERVED reservation may be cancelled or released under
   this revision.  Cancellation, expiry cleanup or revocation cleanup
   MUST atomically prevent every later consumption before releasing
   outstanding authority or facts.  If a consumption already won the
   order, the operation remains charged.  A timeout, disconnected socket
   or cancellation notification is not evidence that this transition
   occurred.

   [R12] COMMITTED, COMPLETED and UNKNOWN authority MUST remain charged
   under the gross-cost policy of revision 0.1.  UNKNOWN facts MUST
   remain in cumulative evaluation.  A provider receipt that only
   establishes acceptance MUST NOT be presented as proof of completion.
   Refunds, compensation and periodic replenishment require a different
   explicit policy and are not implied by these states.

   A caller that loses an acknowledgement MUST perform authorized lookup
   using the same operation identity.  Registry uncertainty at the
   caller is not a new registry state.  The registry may still show
   RESERVED or COMMITTED.  If the authoritative result cannot be
   obtained, the caller MUST suspend further action that would duplicate
   the operation or assume its budget was released.

   Lookup and retry MUST validate tenant and invoker access.  A matching
   operation identity with a different bound action is a conflict.  A
   matching already-committed operation MAY return its existing receipt,
   but MUST NOT cause a second effect.

4.  Intent and Constraint Token

   An ICT is a JWS Compact Serialization token using the JWT claim model
   [RFC7515] [RFC7519].  It is transported as integrity-protected
   constraint context and MUST NOT replace the access credential
   required by MCP or by a downstream resource.  The base profile
   deliberately has one cryptographic suite to avoid ambiguous
   negotiation.

   configured P-256 verification key authorized for the issuer and token
   role, and verify the original received JWS signing input.  The
   signature is the 64-octet R || S encoding required by [RFC7518], not
   an ASN.1 DER signature.  An unrecognized kid, retired key or
   unavailable trust configuration MUST cause refusal or suspension.

   The protected header contains exactly alg, kid and typ.  Additional
   header members, including crit, jku, x5u, jwk and b64, are
   unsupported in this revision and MUST be rejected.  The none
   algorithm, symmetric-algorithm substitution, an embedded untrusted
   key and key retrieval from a token-supplied URL MUST NOT be accepted.

   The strings zti-ict+jwt and zti-mandate+jwt are private, explicitly
   agreed type discriminators, not registered media types.  Their role-
   specific validation rules are mutually exclusive through the required
   typ and claim schema, including when authority and provider services
   share a host or audience identifier.  Verifiers MUST apply those
   rules, following the separation guidance of [RFC8725].  Algorithm
   agility requires a new explicitly supported profile revision, not an
   untrusted header override.

4.3.  Action_Binding envelope

   The canonical envelope contains exactly profile, tenant_id,

   contract used to interpret the action.

   arguments MUST be the final effective arguments, including required
   defaults and provider preconditions.  An adapter MUST NOT strip or
   rewrite semantically relevant fields after the binding.  A change of
   executor, resource, tool revision, arguments, tenant, mandate or
   operation identity requires new authorization.

   JSON-RPC request IDs, transport connection IDs and observational
   tracing headers are excluded because they do not define stable
   operation identity.  All metadata and provider preconditions that
   change the protected action MUST be included in the envelope,

   directly or through an immutable reference or digest included in it.
   The provider MUST resolve and enforce that same committed

4.4.  Selective disclosure and zero-knowledge proofs

   Zero-knowledge proofs and selective-disclosure credentials are not
   defined by the baseline.  Implementations MUST NOT replace the
   required online registry check with a claim that a general intent
   proof exists.  A future proof binding would need an explicit
   predicate, witness, issuer trust model, freshness and revocation
   semantics, action binding, disclosure policy and conformance vectors.

   An optional semantic assessment MAY influence whether the authority
   issues a mandate or reserves an action.  Its scores, false positives,
   false negatives and abstention behavior MUST be evaluated separately
   from the transactional requirements.  The mandatory Vectorial Gate
   below contains no embedding distance or psychological inference.

5.  Deterministic Vectorial Gate

   Vectorial denotes a vector of explicitly measured dimensions and a
   set of authoritative facts.  It does not denote an embedding model.
   Let B be the root budget vector, D the sum of charges consumed at
   COMMITTED, R the sum of unconsumed active reservations, and F the
   union of consumed facts and all facts still possible from active
   reservations.

   [R17] Admission MUST evaluate every root dimension componentwise and
   reject if D[k] + R[k] + c[k] exceeds B[k].  It MUST also reject when
   any root forbidden_set is a subset of F union candidate_facts.  The
   entire read, evaluation and reservation update MUST be one ordered
   state transition.  Checking each action in isolation is non-
   conforming.









Messaoudene                Expires 4 May 2027                  [Page 16]

Internet-Draft                   ZTI-MCP                    October 2026


   A forbidden_set is a nonempty set of unique positive labels.  Every
   member must be in the deployment's authoritative fact vocabulary.
   The root predicate is monotone: adding facts cannot turn a forbidden
   state into a permitted state.  Removing a cancelled reservation's
   possible facts is permitted only under the safe cancellation rule.
   Historical consumed facts are never erased in revision 0.1.

   RESERVE(authenticated_invoker, envelope):
     begin ordered transaction for envelope.root_mandate_id
     resolve and validate current complete mandate lineage
     require invoker == current mandate.delegatee_id
     reject duplicate operation with different envelope digest
     return existing reservation/result for an identical retry
     derive trusted costs c and possible facts f
     enforce all ancestor allow-sets, per-action caps and validity
     read D, R and F from authoritative root state
     require for every k: D[k] + R[k] + c[k] <= B[k]
     require no forbidden_set is a subset of (F union f)
     create RESERVED record bound to envelope, c, f and identity
     commit reservation transition
     issue role-specific ICT for that stored reservation

   The gate treats an outstanding reservation as a possible future
   effect.  If action A reserves fact sensitive_read, a second action
   whose possible facts contain external_export is rejected when the
   root prohibits {sensitive_read, external_export}, even when A has not
   yet committed.  This is a conservative policy example, not a
   statement that every sensitive read or every export is intrinsically
   prohibited.

   The labels must be obtained from a trusted catalogue, versioned
   resources or equivalent authoritative provider evidence.  The system
   cannot establish this guarantee if agents freely choose or omit their
   own labels.  False classifications and incomplete catalogues are
   explicit limitations of the deployment.

5.1.  Revalidation and atomic consumption














Messaoudene                Expires 4 May 2027                  [Page 17]

   ATOMIC_EFFECT(authenticated_invoker, ict, final_envelope):
     validate JWS type, signature, fixed issuer and recipient
     enter the provider/registry protected authorization unit
     load the exact authoritative operation and reservation
     validate current root and complete ancestor status

     atomically:

   [R18] Revalidation MUST NOT add its own existing reservation a second
   time.  Consuming it transfers authority from R to D while preserving
   D + R.  A changed footprint MUST be rejected and newly authorized
   before effect; a provider MUST NOT execute first and retroactively
   increase the charge to make a violation appear compliant.

   If the protected operation fails before the atomic boundary, the
   implementation can retain or safely cancel its reservation.  If it
   may have crossed the boundary, recovery MUST use authoritative lookup
   and preserve its possible or consumed charge.  Infrastructure failure
   MUST NOT be counted as a successful policy refusal.

   A receipt MUST contain profile, tenant_id, root_mandate_id,
   mandate_id, operation_id, reservation_id, action_hash,
   effect_boundary, status and state_revision. profile is zti-mcp/0.1;
   effect_boundary is resource-mutation or provider-acceptance as fixed
   by the trusted provider contract; status is COMMITTED, COMPLETED or
   UNKNOWN.  The other fields use their previously defined types.  A
   receipt MUST be delivered over an authenticated channel or have a
   separately specified authenticated envelope.  It records the claimed
   boundary outcome, not a universal proof of external completion.

5.2.  Conditional safety argument

   Assume a reliable root registry, complete mediation, truthful
   conservative footprints, exact non-negative arithmetic and unique
   consumption.  Initially D = R = 0.  Admission adds c only when D + R
   + c <= B.  Consumption transfers c from R to D.  Safe cancellation
   removes only an unconsumed reservation that cannot later be
   exercised.  Consequently D + R <= B is preserved by these
   transitions.




Messaoudene                Expires 4 May 2027                  [Page 18]

Internet-Draft                   ZTI-MCP                    October 2026


   For forbidden sets, admission checks the union containing all
   possible reserved effects.  Consumption does not introduce a fact
   outside that reserved set.  Safe cancellation only removes effects
   made impossible.  A forbidden positive combination therefore cannot
   appear through a conforming admitted transition under the footprint
   assumptions.

   These are conditional invariants of the stated transition system.
   They do not prove a classifier correct, infer unknown activities,
   establish a global real-world intent property or demonstrate that a
   remote provider implements AtomicEffect.  The experiment and
   implementation report must be evaluated separately.

6.  Concurrency, Revocation and Failure Semantics

   [R19] The registry MUST provide a linearizable order for conflicting
   transitions within a root, including reservation, cancellation, root
   or ancestor revocation, consumption and administrative status
   changes.  A set of eventually consistent counters or independent per-
   agent balances does not satisfy this requirement.  Implementations
   MAY shard independent roots but MUST NOT claim a shared bound across
   those roots without an additional authority policy.

   The profile does not choose a consensus algorithm.  A deployment
   report MUST specify the storage and failover mechanism that preserves
   the required order.  A replicated implementation that cannot
   establish current authority during a partition MUST suspend protected
   effects rather than silently accept a cached positive decision.

6.1.  Revocation ordering

   [R20] Root revocation MUST make the root inactive and advance its
   authority epoch in the same ordered state domain used by consumption.
   At the maximum representable epoch, it MUST instead make the root
   terminally inactive without wrapping to zero; saturation MUST NOT
   leave revoked authority usable.  Ancestor revocation MUST make that
   ancestor inactive so that every descendant consumption fails its live
   lineage check.  An ICT epoch match alone is not a substitute for
   checking revoked intermediate mandates.

   The authority epoch changes on an authority decision, not on ordinary
   reservation, consumption or cancellation bookkeeping.  Those
   transitions update the state revision and are still read atomically.
   If a bounded state revision saturates, the implementation MUST
   suspend new protected transitions and retain a terminal inactive or
   equivalent safe representation for revocation, rather than wrap or
   reset its history.




Messaoudene                Expires 4 May 2027                  [Page 19]

Internet-Draft                   ZTI-MCP                    October 2026


   The revocation operation MUST return an authenticated acknowledgement
   identifying the scope and authoritative revision at which it became
   effective.  No consumption ordered after that revocation may use the
   revoked authority.  A request merely sent to a network endpoint is
   not the revocation linearization point.

   If consumption was ordered first, the protected effect or irrevocable
   acceptance may already exist.  Its completion may continue after the
   revocation acknowledgement.  Cancellation of accepted external work,
   if available, is a separate provider operation and does not erase
   historical consumed authority.

   This is the precise meaning of immediate revocation in the profile:
   it takes effect in the common authority order without accepting
   subsequent stale consumption.  It is not a zero-latency physical
   broadcast or retroactive reversal of committed effects.

6.2.  Replay, uncertain acknowledgements and durable state

   [R21] A stable operation identity MUST survive transport retries,
   token resigning, process restarts and acknowledgement loss.  The
   registry MUST prevent a second protected effect under a consumed
   reservation.  It MUST refuse operation identity reuse with a
   different action.  Authorized lookup MAY return an already committed
   result without re-execution.

   The implementation MUST retain replay and accounting records for as
   long as an operation can still be retried, observed or completed
   under its provider contract.  Deletion or compaction MUST preserve
   the safety-relevant tombstone or equivalent durable fact.  The base
   profile does not define safe reclamation for arbitrary providers.

   A trusted time failure, unavailable registry, unresolved mandatory
   ancestor, unavailable key or unknown effect footprint produces
   SUSPENDED or a policy-specific refusal without effect.  A user-
   visible timeout MUST NOT be represented as a verified refusal when an
   effect may already have been accepted.

   Availability is intentionally subordinate to the stated authorization
   property during loss of current authority.  Operators SHOULD bound
   queue sizes, pending reservations and resource consumption, and
   SHOULD provide authenticated resolution and appeal mechanisms for
   prolonged suspension.

7.  Security Considerations and Observability Limits

   The adversary may control a proposer, fragment a task among agents,
   omit claimed context, replay tokens, substitute arguments or
   destinations, attempt to widen a child mandate, race simultaneous
   reservations, choose misleading task labels, exploit timeouts or try
   to omit the profile.  The adversary may also provide hostile tool
   output or policy-looking natural language.  Such material is
   untrusted data.

   [R22] The implementation MUST prevent access to protected effects
   through unmediated alternate paths under the same claimed scope.
   Administrative access, direct database writes and provider backdoors
   are outside the stated guarantee unless the deployment actually
   mediates them.  It MUST disclose these exclusions rather than
   implying network-wide prevention.

   The authority and enforcement adapters are trusted to execute their
   contract.  Compromise of their signing keys, registry state or
   resource classification can defeat the profile.  Key rotation,
   revocation and incident response SHOULD be supported, but possession
   of a signature does not prove that the signer is uncompromised.

   Unique consumption prevents a second effect under the same
   Operation_Key.  It does not automatically recognize that two newly
   authorized operation identities describe the same real-world
   intention.  Semantic deduplication and provider business identifiers
   require their own policy.  A caller MUST NOT evade unresolved-outcome
   recovery simply by allocating a fresh operation identity.

   Open-weight and proprietary models are treated identically as
   proposers.  The profile does not assume either category is
   intrinsically safe or malicious.  A local model can still act on
   resources it controls outside the administered perimeter; ZTI-MCP
   cannot remove that authority by naming a protocol.

   Action digests do not authenticate semantics.  Incorrect tool
   catalogues, mutable resources without checked preconditions,
   undocumented defaults, response-dependent hidden actions and
   incomplete effect footprints can invalidate the assumptions.  Multi-
   stage tools MUST expose separately protected boundaries or reserve a
   conservative footprint for the complete operation.

   A signed, incomplete trace remains incomplete.  A correlation
   identifier does not prove that every related activity belongs to the
   observed root.  Two independently granted roots can collectively
   exceed a desired global limit while each respects its own policy.
   Root issuance and cross-root allocation require separate governance.



Messaoudene                Expires 4 May 2027                  [Page 21]

Internet-Draft                   ZTI-MCP                    October 2026


   The profile may conservatively refuse a harmless operation because
   another reservation could combine with it.  Unknown labels and
   suspended state can reduce availability.  These consequences MUST be
   reported separately from successful detection of an actual harmful
   purpose.  A policy or classifier error is not repaired by signing its
   result.

   The predicate language in revision 0.1 intentionally uses finite
   positive labels and monotone forbidden sets.  Arbitrary executable
   policies, negative facts, sequence-dependent obligations,
   probabilistic risk thresholds and learned embeddings are outside the
   mandatory gate.  An extension defining them would require new
   semantics and evidence.

   [R23] Parsers and verifiers MUST impose explicit input size, nesting,
   lineage and pending-state limits.  They MUST reject duplicate members
   and unsupported mandatory values.  They MUST NOT fetch issuer URLs,
   key URLs, schema references or registry endpoints supplied by an
   untrusted token without an authenticated configured trust
   relationship.

   No statement in this document establishes criminal intent, legal
   compliance, liability immunity, patentability or a universally safe
   assembly of actions.  The specified properties concern the declared
   policy, observed scope and trusted integration.

   reservation may be safely cancelled through the authoritative
   transition before a separately authorized new operation is created.
   An application MUST NOT assume that merely obtaining a new token or
   changing an operation ID resolves an uncertain accepted operation.

8.3.  Transport mapping and provider integration

   For Streamable HTTP, the normal Authorization credential remains
   separate from the ICT.  Required MCP-Protocol-Version, Mcp-Method
   and, for tools/call, Mcp-Name headers MUST match the corresponding
   message data as required by the pinned MCP transport specification
   [MCP-HTTP].  The profile defines no parallel HTTP header carrying the
   entire mandate or history.

   For stdio, the same JSON metadata is used.  The host MUST establish
   an authenticated local invocation identity and protect the provider/
   registry channel against substitution.  The existence of a long-lived
   process or connection MUST NOT stand in for a root, task or
   authenticated principal.  The HTTP OAuth procedure is not
   automatically imported into stdio [MCP-AUTH].

   A gateway MAY mediate both MCP and non-MCP downstream providers, but
   each provider binding MUST preserve the final action and satisfy
   AtomicEffect.  Wrapping an arbitrary HTTP API with MCP does not
   create atomic authorization.  Unsupported providers MUST be excluded
   from strict coverage or rejected for protected effects.

   metadata mismatch uses -32020.  Implementations MUST NOT appropriate
   reserved MCP error codes for unrelated ZTI outcomes.

8.5.  Relationship to Interceptors and adjacent work

   Interceptors is informative prior work, not a dependency.  The
   comparison in this draft is pinned to SEP-2624 at commit
   3a2760642010e30037231ef4d7586750b0654e65.  Its receiving sequence
   places validation before mutation, and its execution options include
   audit and fail-open behavior.  An integration claiming this profile
   therefore needs final-action verification after relevant
   transformations and mandatory blocking at the protected boundary
   [INTERCEPTORS].

   The atomicity of an interceptor mutation chain does not establish
   atomicity with a provider effect or shared registry.  The required
   ZTI final gate is an additional integration contract; this document
   does not claim that the examined proposal already specifies it.  An
   invoker override MUST NOT disable that gate while retaining strict
   conformance.

   OAuth Rich Authorization Requests describes structured rights
   [RFC9396], while OAuth Token Exchange defines subject/actor
   relationships without automatically consuming input authority or
   propagating all revocation [RFC8693].  UCAN separates delegation and
   invocation and includes attenuation and execution-time validation
   [UCAN].  Verifiable Intent defines signed commercial mandates and
   cumulative budget tracking [VI].  These mechanisms are relevant
   antecedents.  This draft claims neither invention of signed mandates
   nor first use of cumulative authorization.

9.  Privacy and Operational Considerations

   [R26] A deployment MUST define the data it records, the parties
   allowed to query it, retention limits and deletion rules that
   preserve safety-relevant state.  Mandate chains and cumulative facts
   can reveal relationships and sensitive activities.  Access to
   registry lookup and audit results MUST be authorized per tenant and
   principal.

   Providers SHOULD receive only the information needed for their
   contract.  Hash commitments SHOULD be treated as potentially
   identifying data: a hash of a predictable value does not conceal that
   value against guessing.  Logs SHOULD exclude raw OAuth credentials,
   ICTs and sensitive arguments when a protected reference suffices.





Messaoudene                Expires 4 May 2027                  [Page 28]

Internet-Draft                   ZTI-MCP                    October 2026


   Signed tokens provide integrity rather than secrecy.  Confidentiality
   of transport and stored state depends on the authenticated channel
   and storage controls.  A shared registry is a concentration of
   operational and privacy risk; deployments SHOULD document
   administrative access, failure handling, monitoring, backup and
   incident procedures.

   Operational reporting SHOULD separate invalid requests, genuine
   policy refusals, unknown footprints, infrastructure suspensions,
   committed actions and uncertain outcomes.  Counting every timeout as
   a prevented attack would misrepresent the system.

10.  Conformance and Implementation Evidence

   [R27] A conformance claim MUST name the profile revision, MCP
   binding, protected operations, issuer trust configuration,
   authoritative footprint source, registry ordering mechanism, time
   policy, provider effect boundary and recovery behavior.  Support for
   parsing an ICT or advertising an extension is not sufficient.

   *  Positive execution: a permitted action must produce the declared
      protected transition and a corresponding durable receipt.

   *  Attenuation: a child cannot widen an ancestor restriction, change
      a unit, reset a root or replace a cumulative policy.

   *  Concurrency: two individually valid proposals cannot jointly
      exceed a shared dimension or create a forbidden combination
      through outstanding reservations.

   *  Current authority: root and intermediate revocation, expiry and
      changed preconditions prevent later consumption in the defined
      order.

   *  Binding and replay: changes to action, identity, audience or scope
      fail; resigning identical claims cannot produce a second effect.

   *  Recovery: acknowledgement loss, cancellation races and UNKNOWN
      preserve the correct single charge and possible facts.

   *  Compatibility: missing profile, unsupported revision, unavailable
      authority and disabled final enforcement do not silently weaken
      the contract.

   The R4 companion experiment is a bounded local implementation,
   described in an implementation report shipped with this draft.  It is
   not the normative specification.  It uses local SQLite for the tested
   effect boundary, signed fixture credentials and a restricted



Messaoudene                Expires 4 May 2027                  [Page 29]

Internet-Draft                   ZTI-MCP                    October 2026


   canonicalization corpus.  Its exact test counts, mutations, source
   digests and observed failures are recorded in that report, rather
   than inferred from the normative requirements.

   The local tests do not establish production MCP SDK interoperability,
   full JCS coverage, external-provider atomicity, complete crash
   recovery, distributed consensus, classifier accuracy or independent
   institutional certification.  A public maturity claim requires a
   provider binding, at least one genuinely independent implementation
   and a reviewed interoperability corpus covering the selected profile.

11.  IANA Considerations

   This individual experimental draft requests no IANA actions.  The JWT
   claims zti and zti_mandate and the type discriminators zti-ict+jwt
   and zti-mandate+jwt are private values used by explicit agreement.
   No new registered media type, OAuth parameter, URI scheme or IANA-
   assigned error code is claimed.

   The metadata identifier EXT_ID is a deployment-controlled MCP
   extension identifier. org.example/zti-mcp is illustrative reserved
   example space and MUST NOT be advertised as an assigned production
   namespace.  A future proposal for public registration or official MCP
   extension status requires its own registration text and review.
